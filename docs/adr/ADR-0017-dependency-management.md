# ADR-0017: Dependency management: find_package first, opt-in pinned FetchContent

- Status: Accepted
- Date: 2026-11-10
- Supersedes: none
- Superseded by: none
- Amended by: [ADR-0043](ADR-0043-json-schema-dialects-and-validator.md) (the JSON Schema validator is jsoncons, not json-schema-validator)

## Context

The default build must work offline and must work with system package managers. Developers without the dependencies installed still need a way to build, but never silently.

## Decision

- Dependencies come from `find_package` (CONFIG mode). Floors: `nlohmann_json` 3.11, `jsoncons` exactly 1.10.0, `yaml-cpp` 0.8 (0.7 through a target shim), `spdlog` 1.10, `GTest` 1.11, `SWIG` 4.0, `Python3` 3.10. The floors are provisional (OQ-12).
- All third-party dependencies link PRIVATE to the runtime; public headers expose none of their types.
- `PRAENORA_FETCH_DEPENDENCIES` is OFF by default. When ON, `FetchContent_Declare(... GIT_REPOSITORY ... GIT_TAG <commit> FIND_PACKAGE_ARGS <floor> CONFIG)` is used, so installed packages are used first and only missing ones are downloaded. `GIT_TAG` is the commit, with the tag in a comment. Fetched sub-projects build with `CMAKE_POSITION_INDEPENDENT_CODE ON`.
- Pinned versions:

- Package managers (Homebrew, apt/dnf, conda-forge, vcpkg) feed `find_package` where they package a dependency; the developer guide gives commands per platform. jsoncons is in vcpkg and the distributions only at versions older than its floor (1.9.0 and 1.3.2 to 1.5.0 when this was checked), so it comes with `PRAENORA_FETCH_DEPENDENCIES=ON` or from an installation of the developer's own.
- `BUILD_SHARED_LIBS` is never read: the runtime is always `SHARED` and modules are always `MODULE`.

### Builder notes (Proposed)

- `find_package` and `FIND_PACKAGE_ARGS` request the minimum versions listed, except that yaml-cpp is requested at 0.7. Version 0.7 exports only the unnamespaced `yaml-cpp` target, and the shim makes it usable; 0.8 and newer export `yaml-cpp::yaml-cpp`. A yaml-cpp older than 0.8 produces a status note during configuration. The target shim aliases `yaml-cpp::yaml-cpp` to `yaml-cpp` for packages that export only the older name. jsoncons, which has no install-rule option, is fetched without being added as a project: only its sources are downloaded (`SOURCE_SUBDIR` names a directory without a `CMakeLists.txt`) and an interface target for its include directory is defined, so it installs nothing and builds no tests. spdlog is used through `spdlog::spdlog` when present, otherwise `spdlog::spdlog_header_only`.
- The GoogleTest fetch content is named `googletest` and found with `FIND_PACKAGE_ARGS 1.11 CONFIG NAMES GTest`. The name `GTest` would collide with the `gtest_SOURCE_DIR` variable of GoogleTest's own `gtest` project. GoogleTest is made available only when tests are built.
- Fetched sub-projects get `INSTALL_GTEST=OFF`, `gtest_force_shared_crt=ON` (the MSVC runtime of the rest of the build) and `YAML_CPP_BUILD_TOOLS=OFF`; `CMAKE_POLICY_DEFAULT_CMP0077=NEW` makes their `option()` calls honor these values. With CMake 3.25 or newer the fetched content is declared `SYSTEM`. Position-independent code is switched on only while the dependencies are made available.
- Configuration prints one line per dependency: `Praenora: dependency <name> <version> (found at <config directory>)`, or `(fetched into <source directory>)`, or `(local sources at <source directory>)` when FetchContent's cache variable `FETCHCONTENT_SOURCE_DIR_<NAME>` names a local copy of the sources; a fetched or local dependency shows its pinned version, which local sources are not checked against. The dependency's target decides: an imported one was found, any other was built in the tree. A `<name>_SOURCE_DIR` variable does not decide, because a sub-project's `project()` call leaves one in the cache, often under the content's name, which outlives the switch back to an installed package. The spdlog line also names the chosen target.
- Binaries from package managers carry their own minimum macOS version (Homebrew builds for the running macOS release). Linking them below that version makes the linker warn. When the dependency binaries target a newer macOS, a local `CMakeUserPresets.json` sets `CMAKE_OSX_DEPLOYMENT_TARGET` to that version. The project default stays 11.0.
- Both the C and the C++ compiler are checked against the compiler floors (GCC 9, Clang 10, AppleClang 13, MSVC 19.29); a compiler below its floor stops the configuration. A compiler other than GCC, Clang, AppleClang or MSVC produces a warning, not an error, and its version is not checked.
- The installed CMake package `Praenora` (`cmake/PraenoraConfig.cmake.in`) has the components `ModuleSDK` (the export set `PraenoraModuleSDKTargets` and `PraenoraModule.cmake`) and `Runtime` (the export set `PraenoraRuntimeTargets`); `find_package(Praenora)` without components loads both. An unknown component is not found; when it is required, neither is the package, and `Praenora_NOT_FOUND_MESSAGE` names it and the two components, so the reason appears in the error. That holds whatever the component's name: `if()` reads a variable that holds a CMake false constant (such as `No`, `Off` or a value that ends in `-NOTFOUND`) as false, and takes an argument that ends in `-NOTFOUND` for a false constant without reading the variable it names. So the configuration never hands `if()` a list of component names, or the name of a variable named after a component, to read as true or false: it compares lists with `""` and reads `Praenora_FIND_REQUIRED_<component>` by its value, 1 or 0, in quotes. It decides `Praenora_FOUND` itself instead of calling `check_required_components()`, which hands `if()` that name and would accept a required component named `Frobnicator-NOTFOUND`; the package is configured with `NO_CHECK_REQUIRED_COMPONENTS_MACRO`, so the installed file does not define that macro. The `ModuleSDK` component looks for no other package and does not define `Praenora::Runtime`, and `Runtime` does not define `Praenora::ModuleSDK`. The install test checks each: consumer-module requires `PACKAGES_FOUND` to be just `Praenora` and `PACKAGES_NOT_FOUND` to be empty after its `find_package(Praenora COMPONENTS ModuleSDK)`, both consumers check the targets they got, and a project that requires an unknown component must fail with that reason, also when the component is `Off` alone or `Frobnicator-NOTFOUND` next to `Runtime`; a project that requires `Runtime` and names the optional component `Frobnicator-NOTFOUND` must find the package, with `Praenora::Runtime` and without `Praenora::ModuleSDK`; and a project that names no component must get both targets.
- No `find_dependency()`: neither component needs a third-party package. The install test settled it: the exported `Praenora::Runtime` carries only its include directory and `cxx_std_17`, with no `INTERFACE_LINK_LIBRARIES` and no `IMPORTED_LINK_DEPENDENT_LIBRARIES`. The runtime links its third-party libraries privately through the INTERFACE target `praenora_runtime_deps`, and CMake records a shared library's private dependencies for its importers only when they are shared-library targets it links directly. An application built against the installation with only Praenora found configures, links and runs (macOS, where the runtime finds yaml-cpp, spdlog and fmt by their absolute install names). Not yet verified: on Linux, CMake therefore adds no `-rpath-link` for those libraries when a consumer links the installed runtime, so libraries from the distribution's packages (default directories) are found, while libraries in other directories need the consumer's `-rpath-link` or `LD_LIBRARY_PATH`. On Windows they are installed beside the runtime's DLL (ADR-0019).
- The install test (`tests/install`, CTest `install.consumer`) configures its two consumer projects with the build's generator, compilers, build type, macOS architecture and deployment target, and `CMAKE_PREFIX_PATH` = the installation followed by the build's own dependency prefixes, through an initial-cache file, and checks that each found Praenora in the installation (`Praenora_DIR`). The consumers also get the build's `CMAKE_<LANG>_FLAGS` (C, C++) and `CMAKE_<EXE|SHARED|MODULE>_LINKER_FLAGS`, empty ones included, plus its sanitizer options, which `cmake/PraenoraSanitizers.cmake` publishes as `PRAENORA_SANITIZER_COMPILE_OPTIONS` and `PRAENORA_SANITIZER_LINK_OPTIONS`; a consumer of the C++ API must be compiled like the runtime, and the consumers link the instrumented runtime in sanitizer builds, where the test passes too (AddressSanitizer, ThreadSanitizer). The consumers are configured with uninitialized variables reported (`-Wuninitialized`, `--warn-uninitialized` before CMake 4.4) and `--check-system-vars`, without which files outside the consumer's own trees, such as the installed ones, are not checked. Only `PraenoraConfig.cmake` and `PraenoraModule.cmake`, which this project writes, must be clean; a warning that names either file fails, in both forms CMake writes, `at <file>:<line>` and `in <file>:` (a read in an `elseif()` condition). The target files CMake generates read an unset variable themselves (`_cmake_import_check_xcframework_for_<target>`, CMake 4.4), as do CMake's own modules. The drivers of the CLI, install, perf and provider-file tests run commands through one script, `tests/support/run_command.cmake`, which also decides what counts as a sanitizer report.
- With `PRAENORA_FETCH_DEPENDENCIES=ON`, the fetched projects' own install rules are switched off before `FetchContent_MakeAvailable` (`JSON_Install`, `YAML_CPP_INSTALL`, `SPDLOG_INSTALL` set OFF; `INSTALL_GTEST` already was): they are header-only or static libraries used privately by the shared runtime, so neither `cmake --install` nor a wheel may carry their headers, libraries or CMake files. Not yet verified: the option names are taken from the upstream projects and could not be checked offline. A fetch-mode configuration with every package installed finds them all with `find_package` and fetches nothing.
- Fetch mode also makes the fetched libraries static, whatever a super-build's `BUILD_SHARED_LIBS` says: a fetched shared library would be neither installed (their install rules are off) nor found by an installed runtime. Before `FetchContent_MakeAvailable`, each project's own shared-library option is set OFF (`YAML_BUILD_SHARED_LIBS`, `SPDLOG_BUILD_SHARED`), and so is `BUILD_SHARED_LIBS`, because the per-project options alone cannot guarantee static libraries: some projects build a shared library when either their own option or `BUILD_SHARED_LIBS` is on, and others call `add_library()` without a type. `BUILD_SHARED_LIBS` is set as a normal variable for that call only and unset right after it, never read, so this project's own targets keep their explicit types (the runtime `SHARED`, modules `MODULE`). The unset also removes, for the rest of the Praenora directory scope, a normal `BUILD_SHARED_LIBS` variable that a parent project set; nothing in that scope reads it. Not yet verified: the other projects' option names are taken from the upstream projects, and no download has been made to check them or to build the fetched libraries.
- `PRAENORA_FETCH_JSON_SCHEMA_VALIDATOR`, which built the previous validator in the tree for sanitizer builds, is gone: the validator is header-only and compiled with the tree's flags ([ADR-0043](ADR-0043-json-schema-dialects-and-validator.md)).

## Alternatives considered

- **Always fetch.** Breaks offline builds and the no-network default.
- **Vendoring sources in the repository.** Offline, but inflates the repository and complicates updates.
- **Git submodules.** Needs network for checkout and offers no installed-package preference.
- **A package manager as a hard requirement (vcpkg or Conan).** Excludes users of other managers.

## Consequences

- Default builds never touch the network.
- Pins by commit are immune to moved tags.
- Pins must be refreshed deliberately, and fetch mode is verified only when network access exists.
