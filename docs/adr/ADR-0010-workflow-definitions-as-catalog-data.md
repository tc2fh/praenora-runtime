# ADR-0010: Workflow definitions as versioned catalog data; YAML config binds steps to modules

- Status: Accepted
- Date: 2026-11-10
- Supersedes: none
- Superseded by: none
- Amended by: [ADR-0043](ADR-0043-json-schema-dialects-and-validator.md) (the schemas the runtime ships, and a module's `parameters_schema`, may be 2020-12; the reference below is the draft-07 text this ADR was written against)

## Context

Topology must not be hard-coded in the runtime or repeated in every user file. Users need a simple file to bind modules and parameters, and the project requires that connections come from the workflow version and the protocol, never from the YAML.

## Decision

- Workflow definitions, capabilities and message types are versioned catalog entries (`spec/catalog/`), shipped and embedded with the runtime. Extra directories can add entries (`--catalog-path`).
- A workflow definition holds typed steps (each requires one capability), workflow inputs and outputs, and connections (`from`, `to`, optional `delay`).
- The workflow configuration (YAML, `kind: workflow-config`) pins one workflow definition by name and version, binds every step to a module (name, exact version) with parameters, binds every workflow input to a data source, and sets run, output and observability options. No more and no fewer steps may be bound than the definition has.
- The YAML is converted to JSON with a JSON-pointer to line and column map and validated against its schema (ADR-0008); errors name file, line, column and pointer.
- Document limits: a document file is limited to 16 MiB and JSON or YAML nesting to a depth of 128. Exceeding either is reported as `PARSE_ERROR` rather than parsed. (Builder note, Proposed.)
- Precedence: CLI flags, then environment variables, then configuration file, then defaults. Run settings overridden from the CLI or API are recorded. `outputs` and `observability` never affect the run fingerprint.
- Identifier patterns: module names and catalog ids `^[a-z][a-z0-9-]*(\.[a-z][a-z0-9-]*)*$`; step ids and port names `^[a-z][a-z0-9_]*$`; `inputs` and `outputs` are reserved.
- Static graph rules (unique producers per input, type equality, required inputs connected, delayed connections only into optional inputs, acyclic delay-0 subgraph) are specified in [docs/specs/workflow-definitions.md](../specs/workflow-definitions.md).

### Builder notes (Proposed)

- YAML subset details: the explicit tags `!!str`, `!!int`, `!!float`, `!!bool` and `!!null` are honored and every other tag (including `!!map`, `!!seq`, `!!binary` and local tags) is a `PARSE_ERROR`; mapping keys must be non-null scalars and keep their text (`1: a` has the key `"1"`); an empty document is a `PARSE_ERROR`; all text must be valid UTF-8. A YAML document may hold at most 2^18 values after alias expansion ("document too large"); the count is taken on the parsed graph before any JSON is built, so a small document with exponentially many aliases fails fast.
- A document whose origin ends in `.json` (any case) is strict JSON: it is parsed by the JSON parser only and never read as YAML, so `{a: 1}`, trailing commas or an unquoted `0.1.0` are `PARSE_ERROR`s. Any other document whose first character is `{` or `[` and that is valid JSON is read by the JSON parser too, so JSON's escapes (including surrogate pairs) and numbers behave exactly as in JSON. Positions of JSON documents come from a scanner over the same text, and duplicate keys are rejected there too.
- Nesting is checked before parsing: brackets are counted on the raw text of every document, and block nesting on the parsed graph. Brackets count everywhere except inside quoted scalars and comments, including inside plain and block scalars, which yaml-cpp reads as text. So as long as the scan splits the text into tokens as yaml-cpp does, its count is at least the flow nesting the parser will find; in exchange, unbalanced brackets inside scalars add up toward the limit. The quoted scalars and comments are found by splitting the text into tokens as yaml-cpp does, so a quote opens a string only where a token starts, never inside a plain scalar (`a:'x`, `don't`); where a scalar ends depends on indentation, which the split follows too. Where yaml-cpp departs from YAML 1.2 the split follows yaml-cpp, the parser it protects: a comment may follow a token directly (`[a]#b`), a node that may be a key opens an indentation level before a colon confirms it, and only the kind of the first line end in the text (`\n`, or a lone `\r`) starts a new column count. In text with a NUL byte (UTF-16 or UTF-32, which yaml-cpp reads too) every opening bracket counts and no closing one; past 4096 levels of block collections the same holds from there on. yaml-cpp's own recursion limit, which it reports as "bad file", is reported as "nesting too deep" as well.
- Source positions are 1-based lines and byte columns. A scalar is located where it starts; a mapping entry whose value is a mapping, a sequence or empty is located at its key; the outermost object or array is nesting level 1.
- Catalog entries are strict JSON documents, one per file: `messages/<id>/<version>.json`, `capabilities/<id>/<version>.json` and `workflows/<name>/<version>.json`. The loader reads the embedded entries (`catalog/...`), then every `*.json` file below each extra directory, recursively and in sorted path order. Every entry is validated against the schema of its kind (`SCHEMA_VIOLATION`, located in the entry: `catalog/<path>` for embedded entries, the file path otherwise), and each message type's data schema is compiled at load time.
- Catalog entries are keyed by kind and `id@version` (a workflow definition's id is its name): a message type, a capability and a workflow definition may share an `id@version`. A second definition of the same kind and `id@version` is `CATALOG_ENTRY_DUPLICATE` (406), and the message names both origins. An extra directory cannot replace an embedded entry. Versions are compared without build metadata. `raw_entry(id, version)` returns the entry only when exactly one kind defines that `id@version` (nullptr when none or several do); `raw_entry(kind, id, version)` selects the kind explicitly.
- An entry's `digest` is `sha256_hex(canonical_json(entry))`. `Catalog::check()` reports `CATALOG_ENTRY_NOT_FOUND` for capability ports and workflow inputs and outputs with unknown message types, and for workflow steps with unknown capabilities.
- Loading a workflow configuration checks, in order: the file is read and parsed (`IO_ERROR`, `PARSE_ERROR`); its `kind` is `workflow-config` (`DOCUMENT_KIND_MISMATCH`, also for a missing kind); `format_version` is a version string (`SCHEMA_VIOLATION` otherwise) that has a schema (`FORMAT_VERSION_UNSUPPORTED`, naming the formats this runtime reads); the document satisfies the schema (one `SCHEMA_VIOLATION` diagnostic per problem, each located). A document that fails any of these yields no configuration. Then the values the schema cannot check are `CONFIG_INVALID`: a duration `parse_duration()` refuses, a version number beyond 64 bits, an empty path, a `columns` key that is not an observation column, `columns` on a `json-document` input, and two observation columns that would read one header (a column that is not remapped reads the header of its own name).
- Defaults are those of the configuration reference (seed 0; time unit `"1"`, start 0, period 1; timeouts 300 s, 60 s, 5 s; log level `info`, format `text`; `status_interval` 1 s). A step's `timeouts` are the run's timeouts with the step's own fields put over them, field by field. Relative paths (input paths, `modules.search_paths`, `outputs.directory`, `log_file`, `status_file`) resolve against the configuration file's directory and are normalized lexically; symbolic links are not resolved. `status_interval: 0` (or `none`) means the status file is written only on state changes.
- `run.ticks` is required (`CONFIG_INVALID`, located at `/run/ticks`, which reports the line of `run` or of the document) when no input binding uses `observation-csv`, because nothing else would end the run; a ticks override from the caller satisfies it.
- The caller's overrides (`WorkflowOptions`) are applied when the configuration is loaded, after the file: `seed` and `ticks` (each at most 2^53 - 1, otherwise `INVALID_ARGUMENT`), `output_dir`, `trace_messages` and `status_file` (relative paths resolve against the current directory). Logging overrides are left to the caller, because the environment variables rank between them and the file. Interface addition: `read_workflow_config(file, report, overrides)` returns `nullopt` for an unusable document; `load_workflow_config(file, report)` keeps its signature.
- `outputs.record`: when the file does not list it, validation fills in every workflow output (sorted by name); a listed name that is not a workflow output is `CONFIG_INVALID` at `/outputs/record/<i>`.
- The validation sequence collects every diagnostic and skips only what depends on a failure: without the workflow definition nothing after the catalog lookup runs; when a capability or message type the definition uses is unknown, the graph is not validated (it would report the same entry again), and neither are the steps and inputs that use the entry; a module or workflow version the loader could not read is not looked up.
- Validation locates each diagnostic where the fix belongs: binding problems at `/steps`, `/steps/<id>`, `/inputs` or `/inputs/<name>` in the configuration; `MODULE_NOT_FOUND` at `/steps/<id>/module`; `PLATFORM_MISMATCH`, compatibility and library problems in the module's manifest, with `step` and `module` set; parameter problems at `/steps/<id>/parameters<pointer>`; unknown catalog references by JSON pointer into the workflow definition (catalog entries do not yet expose their origin, so these have no file).
- Module search with configured paths: when a configuration lists `modules.search_paths`, the search list is rebuilt as the caller's paths, the configuration's, `PRAENORA_MODULE_PATH`, then the installation directory. `RuntimeContext` therefore also holds the `module_paths` and `use_environment` its index was built from (interface addition), an invariant `make_runtime_context(RuntimeOptions)` keeps: it builds the catalog (the built-in entries, then the caller's `catalog_paths`, which must be readable directories, then the entries of `PRAENORA_CATALOG_PATH` that are directories when the environment is used; a directory named twice is loaded once), the module index from the caller's module paths, and the services. A configured search path that does not exist gets one `NOT_FOUND` warning, located in the configuration; one that exists but is not a directory gets the scan's warning instead. The scan's own diagnostics (invalid or shadowed manifests, non-directories on the search paths) are copied into the report as warnings.
- Library files are checked (existence, pinned digest) and hashed during validation without being loaded. The digest is kept per step (`ResolvedStep::library_sha256`, interface addition) and in the reproducibility section, so loading can confirm the file did not change. A `ValidatedWorkflow` owns copies of the manifests its steps point to (`ValidatedWorkflow::manifests`, one per manifest file, interface addition); it still refers to the context's catalog, which must outlive it.
- The draft starting workflow `pmp.continuous-forecast@0.1.0` names its ports as follows: `propose` (`observations`, `model_set`, optional `replenish` → `candidates`), `curate` (`candidates`, `observations` → `survivors`, optional `replenish`), `predict` (`candidates`, `observations` → `predictions`); the `pmp.assess` capability takes `predictions` and `observations` and emits `assessment`. Draft message schemas require only their core fields and accept `x-` extension fields at every level.
- A catalog entry's `status` (`draft`, `stable` or `deprecated`) is informational: validation and runs treat every status alike, and `praenora catalog list` shows it. A draft workflow definition such as `pmp.continuous-forecast` runs once modules for its capabilities exist.
- Two columns read from one header are one problem, reported once, as `CONFIG_INVALID`, when the configuration is loaded. Every observation column reads one header, its `columns` entry or else its own name; the columns that are not remapped take their own names first, so the clash is located at the entry that causes it (`/inputs/<name>/columns/<column>`), and of two entries that name one header, at the one whose column name sorts later. The refused entry is left out of the binding. Validation then builds no source for an input with an error at or below `/inputs/<name>/columns` (nor at its `path`), so `columns: { time: value, value: value }` and `columns: { value: time }` each give exactly one diagnostic. The `observation-csv` source keeps its own check of the same rule (`INPUT_BINDING_INVALID`) as a defensive one, which validation no longer reaches.
- Diagnostics about a catalog entry, unknown catalog references included, are located in that entry: `Catalog::locate()` gives the file the entry was read from (`catalog/<path>` for an embedded entry) with the line and column of the JSON pointer, and `praenora validate` and `praenora graph` print them as `file:line:col`. The parenthesis "catalog entries do not yet expose their origin, so these have no file" in the note above on where validation locates its diagnostics no longer holds.

## Alternatives considered

- **Topology in the YAML.** Flexible for users, but every user file can then disagree with the protocol, and modules cannot be validated against a known contract.
- **Topology in code.** Violates the anti-goal of a hard-coded workflow.
- **A programmatic API only.** Less approachable and no static validation of a file.

## Consequences

- Changing a workflow is a catalog change (a new definition version), not a code change.
- The runtime can validate a configuration without loading any module.
- Users cannot rewire a workflow; they pick a definition version.
- The starting workflow is a draft catalog entry (see [docs/specs/starting-workflow.md](../specs/starting-workflow.md)).
